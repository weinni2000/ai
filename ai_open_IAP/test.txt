Hi,

There's no fully-fledged open-source IAP replacement that I know of, but the hook to redirect IAP calls to your own server is already built into Odoo — no reverse engineering of the client needed.

The override point

In odoo/addons/iap/tools/iap_tools.py:

def iap_get_endpoint(env):

url = env['ir.config_parameter'].sudo().get_param('iap.endpoint', DEFAULT_ENDPOINT)

return url

Set the system parameter iap.endpoint (Settings → Technical → System Parameters) to your own server URL, and every IAP call from that database goes there instead of https://iap.odoo.com.

What your server needs to implement

Just the JSON-RPC routes Odoo actually calls:

/iap/1/balance — return a credit balance

/iap/<service>/<method> — the service endpoints (for AI, this is where you'd proxy to your inference server)

Most practical approach: a thin FastAPI/Flask proxy that implements only the routes the AI module uses, translates the payload to your inference server's format (OpenAI-compatible, vLLM, Ollama, etc.), and returns the response in the shape Odoo expects. Skip credit metering by returning a huge balance.

A few hours of work. The protocol is simple JSON-RPC — grep iap_jsonrpc in the Odoo source to see exactly what each call sends and expects back.

I haven't seen a maintained OSS version on GitHub or in OCA repos.

Hi Nikolaus,

I'm not aware of a public open-source replacement for the IAP server. The AI app's provider calls live in Enterprise code, so reverse-engineering the IAP endpoint would be fragile (it can change with any update) and is also a licence question for Enterprise, so I wouldn't build on it.

Two approaches that do work with your own inference servers:

Override the provider call in a small custom module. Most self-hosted stacks (vLLM, Ollama, TGI, LiteLLM as a proxy) expose an OpenAI-compatible API. Find the method in the ai module of your exact version that builds the request to the LLM provider, inherit it, and point it at your own base URL and model name. Keep the override thin, because that module is changing between 19 and 20, and test tool calling separately: smaller self-hosted models often handle Odoo's agent tools worse than plain chat.
Invert it: keep the agent harness on your side and give it access to Odoo through MCP. Your own model runs in your own client or agent framework (n8n, LangGraph, a custom app), and Odoo only exposes data and actions through an MCP server. Odoo 20 Enterprise ships a native MCP server, but it needs the Custom plan; on Community, 16–19, or Standard-plan Odoo.sh/on-premise you need a module for it. In both cases scope what the agent can see: a dedicated user with only the needed models, and ideally an audit log of every tool call.
If you need Odoo's built-in AI features themselves (AI fields, server actions), go with option 1. If you mainly want your own models to read and act on Odoo data, option 2 is more robust across upgrades.

Disclosure: we build an MCP Server Connector for Odoo 16–20 (OAuth 2.1, per-user access bundles, audit log, rate limit, IP allowlist) that works with any MCP client: Niyu Labs MCP Server Connector. It isn't installable on Odoo Online.
